先说能实锤什么

执行机制已验证：0.32 P 侧主干第 21–39 层处理 128 行尾窗；Engram lookup 前的冗余 zeros 在 6 个对应调用窗口全部消失。两项都能与生产源码对应。
尚不能给出单 PR / 整模型提速百分比。两版的 batch shape、并行执行布局、库/图路径不同，0.30 缺 D 侧。没有请求级时延、同条件开关 A/B 或质量结果。相同测试用例不保证采到相同的 batch。

目前最有价值的性能发现来自第二批数据：长空闲、跨 DP 的同步等待和融合 MegaMoE 长尾，比十几微秒的单算子更值得先排查。报告不会把所有候选优化都标为“已经兑现”。

机制一：后 19 层确实缩到尾窗

11/07 的 0.32 P rank0：每组 40 层主干序列中，前 21 层 HcPre 的 token 维为 8188，后 19 层为 128。每层两次 HcPre，3 组前向共 126 条大 shape、114 条小 shape。按时间排序的序列与源码切入点一致。

推定的主干前向分组，非请求 ID / ProfilerStep ID
在这一组固定 batch 的反事实比较中，主干 layer-token 行数减少约 46.8%：19/40 × (1 − 128/8188)。这是工作量结构的证据，不是 FLOPs、TTFT 或整模型提速百分比。

0.30 的主干 HcPre 每 rank 为 1023 / 1022 / 828 行，QLI/SFA 的局部 head 维也与 0.32 不同，不能将两版 HcPre 总时间直接计算成版本收益。此处验证的是 decoder 尾窗裁剪，未证明 prefix hit 后的 SWA 窗口重建。

先解释大停顿，再追小算子

第二批 P / DP1

MegaMoE 单次 17.8706s，同一 DP 的 Gloo all_reduce 单次 17.9575s，时间高度重叠；另一 DP 有长空闲。

优先检查 EP peer 的 collective 顺序、DP 空闲参与与 profiler 启停/导出。当前是同步/采集停顿候选，不能据此确认死锁或因果方向。

不要被 Computing 的名字带偏

融合 MegaMoE 含专家分发与合并，等待可能落在这条记录内部。把它整段归为“计算覆盖”不意味着矩阵乘法一直忙。

DP0 与 DP1 的前向调用量为 129 vs 1290；窗口不同，不能直接宣称业务负载差了 10 倍。

首轮 metadata 长尾

第二批 P / DP0 的 SparseFlashMlaMetadata：13 条记录，最大 757.467ms，中位数约 234μs。先定位初始化、排队/同步或采集边界，再判断是否为稳态瓶颈。不能只报告平均 58.55ms。

通信统计的证据边界

第二批 P 侧 communication.json 的带宽/传输量字段全部为 0，不能得出链路带宽为零。CSV 还同时有 HCCL 逻辑 op 和底层 AIV/AICPU task；两条 139.442ms 记录可能是同一次通信的不同层次，不能叠加成一次 278.884ms 延迟。

11/09 D 的编译图路径

出现一次 npu_fx_compiler inference，说明存在经过编译包装的执行。这个名字与时长不能直接解释成“JIT 编译用了 473ms”，也不能证明 enable_static_kernel 开启或所有 batch 都命中图。D 的窗口仍有长 Free，应结合请求到达和图执行区间看。

算子对照：先看 shape，再看平均值

默认是路径与记录量对照；严格模式只保留完全匹配的共同项。时间列为 CSV 记录累加值，非请求墙钟；通信父子记录和跨 stream 重叠尤其不能相加解释。比值不是单 PR 的因果收益。

原先 60 个候选 PR，逐项更新证据

“机制已验证”仅有尾窗裁剪、Engram 去清零两项。replay 的多次 API/CP 演进不拆成多个独立提速；显存优化、Store、PCP、图融合需要各自的数据条件。

纠正适用范围：#16731 改通用 QLI adaptor，本 V4.1 调用的是自定义 QLI v3；#18786 改通用 SFA 的 V up-proj，本次同名 TransposeBatchMatMul 多为 DSA O-proj。不能把同名算子减少直接归因给这两个 PR。
