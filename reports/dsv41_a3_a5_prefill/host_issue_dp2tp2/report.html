为什么Prefill调用DecoderLayer？

trace中的nn.Module是PyTorch模块。DeepseekV41DecoderLayer描述模型层的结构，Prefill和增量生成都会调用它；模块名不能用来判断当前请求阶段。

服务阶段这次送入模型什么经过哪些模型层
Prefill批量处理prompt或其中一个chunk，构建所需KV并计算后续token预测使用模型层的因果Attention；bounded replay生效时，后段可只处理尾窗，不能把它理解成所有token必经所有层
Decode增量处理新token并读取历史KV；MTP等路径可一次处理多个候选token继续调用同一组DecoderLayer

V4.1官方架构为CED：20层因果Encoder接20层Decoder，Decoder的全局KV来源于Encoder的最终隐藏状态。两段均可使用DecoderLayer这一代码类，不能仅由类名推断执行阶段。模型的Encoder/Decoder分段与部署P/D实例不是一一对应，bounded replay是否生效仍须核对实际开关和布局。

Tokenizer.encode/decode又是另一层含义：文本与token ID之间的转换。识别本trace的真实Prefill、dummy和生成前向，需结合execute_model/_dummy_run上下文、Attention元数据、输入shape与任务关联。

可确认的原因与当前边界

  • 直接机制已确认：Host元数据阶段晚结束，进入模型后仍逐层下发偏慢，独立Q/KV分支不能同时就绪。不是少创建了辅助流。
  • 相同请求/算子调用规模下，TP2的初始metadata外层比TP0多25.566ms；40层Host推进多63.670ms。DP协调反而更早结束，不能归咎于DP同步等待更长。
  • 整体多流计算重叠：TP2为0.088462ms，TP0为7.420534ms。但目标设备区间分别为447.408ms和463.346ms；重叠少不等于这张NPU的算子更慢，其他rank的排队/等待也会改变重叠形态。
  • 具体热点包括42次build_replay_swa_visible_lens、Event record/profiler包装、current_stream的对象/设备查询和CANN workspace/tiling；这些记录不能简单相加。
  • 现有数据没有CPU线程调度、亲和和频率记录，不能进一步断言物理CPU慢、绑核冲突或GIL竞争。也不能确认无profiler时是否存在同等退化。

关键现场：第0层KV完成后，Q Norm为什么没及时跟上？

为何正常rank有重叠，而TP2没有：队列提前量不同

TP0第0层Q Norm runtime launch早在本rank1900.516320–1900.525670ms完成，设备到1920.306425ms才执行；KV runtime launch也早完成，两条流上的任务都已就绪。

TP2对应Q Norm runtime launch为1920.856210–1920.864140ms，此时KV早已在1920.607610ms完成。该点没有可以同时运行的两份独立工作。正常rank的排队提前量也可能包含跨rank/前序设备等待，更多重叠不自动等于更快。

40层Host推进：TP0为383.783ms，TP2为447.453ms，多63.670ms；主要算子次数一致。相邻dummy窗口里TP2也更慢：step2为359.576 vs304.186ms，step3为363.293 vs309.874ms，说明不只这一次元数据构造受影响。

下一步定位与优化顺序

  1. 同负载做无profiler/轻量NPU采集对照：当前profiler会包装Event.record/wait，短kernel容易被Host记录开销扰动。先验证异常rank、EP最后到达与低重叠是否稳定复现。
  2. 若复现，补主线程CPU调度/迁核/频率、亲和与其他线程争用；本次_host_sys为空，没有这些证据。不能仅凭Python self wall断言GIL或绑核冲突。
  3. 代码侧优先减少同step/SWA组重复visible_lens与元数据构建；核对现有缓存current_stream接口能否替代重复对象/设备查询。区分正确性依赖与多余包装，不能直接删event或wait。
  4. 为预处理下发做最小实验：复用安全的stream/event对象或减少包装/批量下发，验证Q/KV在设备就绪前均已提交。图捕获与异步buffer/event寿命必须独立检查；Prefill不能直接照搬Decode图模式。
  5. 验收不仅看重叠：同时看最后到达rank、层/step墙钟、TTFT/TPOT和吞吐，带profiler用于定位，不带profiler确认收益。

官方Event profiler包装实现；采集安装版本为2.10.0.post7，实际包装和调用栈以本trace为准。
