假设必须补齐的证据对应动作

设备排队或流依赖Host 已提交，Device 较晚执行；其间有前一步任务、同流排队或 EventWait。A5 当前首 HC 的延后有前轮 Device 积压这一证据。找真正占队列或生产数据的任务；优化错误依赖、生产者时延或积压，不能把 launch→start 都记为 Host 工作。
EP/TP 通信或到齐等待同层各 rank 的到达/结束、消息量、链路带宽、专家 token 分布与 kernel 内 PMU。当前 MegaMoE 的结束集中、到达分散符合等待参与，不能量化纯 GMM 占比。先减少 rank skew/负载差，再评估通信算法、拓扑、量化传输及分发/计算重叠。
Cube/Vector 计算受限相同 shape/dtype/layout 的算量、相应引擎实际利用率及 PMU；不同架构的百分比定义必须先对齐。框架侧选更合适融合/布局与合法路径，尝试能互补资源的并行；真正 kernel 算力优化再交算子团队。
HBM/访存受限实际字节流量、DRAM 带宽、缓存/搬运等待与算术强度；不能仅凭某个 MTE ratio 下结论。消减冗余读写、临时 buffer 和布局转换，融合访问；检查 offload/Engram 数据本地性。
小 kernel / launch 密度受限大量短任务的 Host 下发时间与依赖间隙；证明融合减少实际关键路径，而不只降低调用次数。先复用、批量处理与可用融合，再考虑新增算子；核对动态 shape、图模式及编译成本。

最小实验闭环

  1. 固定 A3 基线：代码/镜像、量化、TP/EP、batch、每请求上下文、SWA/缓存状态、DSpark、采样、CPU 绑定不变。先在无 profiler 条件记录服务指标，再用短窗口 profiling 定位。
  2. 一次只改一个因素：先元数据复用或草稿路径其一。固定 warmup、同 seed/相同请求，不用 prefix/Store 命中变化充当收益。
  3. 至少多次交错 A/B：报告每步分布、跨 rank 最大完成时间、长尾和精度；预先固定统计区间，避免只选最漂亮的一步。高开销 Python/module tracing 可能放大 Host 成本，前后采集配置必须一致。
  4. 以完成时间验收：kernel 数减少、重叠增多只是中间证据；最终要缩短同工作包 Worker 完成时间，并在真实 128k/64 并发验证 TTFT/吞吐和稳定性。若瓶颈转移，把新关键路径作为下一轮输入。
当前优先级建议：先闭环“元数据重复工作”和“MegaMoE / 草稿 MoE 的到齐与分支成本”；随后再做局部多流、融合和拓扑。现有证据不支持先把主要精力押在固定坏卡或盲目搬运 A5 算子上。
