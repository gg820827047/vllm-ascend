从 Scheduler 到 DeepSeekV4.1，代码怎样走过去

先记住：vLLM 负责组织请求与执行，vllm-ascend 提供 NPU 平台、Worker、Runner 和模型实现。启动时选好对象，每个 step 再沿这些对象调用；中间会通过继承多次复用 vLLM 的代码。

图 1：启动时如何选中 Ascend 和模型类

这张图表达配置与对象绑定关系，不要求两个插件分支严格按图中某一先后顺序完成。平台注册、模型注册是两个不同机制；它们都在实际 forward 之前准备好。

模型目录的 config.json → architectures 例如 DeepseekV41ForCausalLM，通过 ModelRegistry 映射到 Ascend 实现。模型路径名称、--served-model-name 不是选择 Python 模型类的直接开关。--quantization ascend 主要选择量化处理，也不是激活整个 NPU 插件的唯一开关。

图 2：每个 step 从 schedule 到执行，再回到 Scheduler

主线以 MRV2 + 标准 multiproc + 文本生成 为例。图中“计划返回后提交”“返回后再提交”表示 EngineCore 组织的数据流，不是 Scheduler 或模型直接调用下一个框。实际函数调用看下面代码索引。

跨进程与跨仓库不同：Executor→WorkerProc 经过进程间消息队列；WorkerWrapper→NPUWorker 是同一个 Worker 进程里的 Python 方法调用；Ascend Runner→vLLM Runner 是 super() 父类调用。它们不需要 HTTP 跳转，也不是 KV 通过 Mooncake 传输。

本 step 传下去的是什么

SchedulerOutput（执行计划）
  num_scheduled_tokens: {request_id: 本步要计算多少 token}
  total_num_scheduled_tokens: 上述数量的总和
  scheduled_new_reqs / scheduled_cached_reqs: 请求、token、KV block 等更新
  scheduled_spec_decode_tokens: 待验证的候选 token
  kv_connector_metadata: 本步 KV 加载 / 保存计划

ModelRunnerOutput（执行结果）
  sampled_token_ids、request 对应关系、投机统计、connector 完成信息等

EngineCoreOutputs（更新请求后向前端输出）
  token / 完成状态 / 统计等

AsyncScheduler 不等于另一套模型：未配置自定义 scheduler_cls 时，async_scheduling 决定 Scheduler / AsyncScheduler 类。AsyncScheduler 继承 Scheduler.schedule，增加异步占位与结果更新；EngineCore 的 batch queue 决定怎样流水化提交/回收，二者有关但不是同一个开关。Ascend 自定义 scheduler 启用时可以替换默认类。

图 3：为什么 self.model 会进入 deepseek_v41

Runner 不会在每一步猜“现在是什么模型”。加载阶段已经创建了具体对象；nn.Module.__call__ 负责 hooks 等通用事项，再调用该对象的 forward。下面展示文本请求的主要计算关系，省略视觉塔、LoRA 与部分并行分支。

Prefill / Decode 都可以经过 DecoderLayer.forward。DecoderLayer 是模型结构名称，不表示“这里只能在 D 节点执行”。Prefill 的长 query/chunk、Decode 的短 query、KV 历史长度与元数据会让后端分支和 shape 不同。

采样与 DSpark 为什么又走一条链

EngineCore
  → Executor.sample_tokens  ──IPC──→ WorkerProc / Wrapper
  → NPUWorker.sample_tokens
  → Ascend NPUModelRunnerV2.sample_tokens
  → vLLM 父类 GPUModelRunner.sample_tokens
      → sample → 已加载模型.compute_logits → sampler / 投机验证
      → [配置了 speculator 时] speculator.propose
          → Ascend DSpark 适配 → 另一份 DSpark 草稿模型实例.forward
          → 草稿 logits / 采样
      → ModelRunnerOutput 经 RPC 返回 EngineCore
  → Scheduler.update_from_output → 完成 / 下一 step

因此 profiling 看到两层 execute_model、多层 wrapper.forward，不是做了多遍主模型。目标模型 40 层与草稿 3 层是不同模型实例的调用。本次采样路径也不能自动解释为每个中间 Prefill chunk 都向用户输出了一个 token；哪些输出有效由请求进度与调度/采样逻辑决定。

MRV1、MRV2、图模式与 P/D 放在哪里理解

情况路径变化保持的结构
MRV2（本文主线）Ascend worker/v2/model_runner.py → vLLM worker/gpu/model_runner.py；准备过程使用 Ascend ModelStateScheduler → Executor → Worker → Runner → 具体模型
MRV1Ascend worker/v1/model_runner.py → vLLM 旧 worker/gpu_model_runner.py；旧 trace 可能叫 model_runner_v1.py同一个 NPUWorker 选择另一个 Runner；不能逐行套用 MRV2 的内部方法顺序
Eager / PIECEWISE / FULLRunner 的 forward 分派不同；FULL 主要回放捕获的图，不一定每次重新出现完整 Python 层栈模型仍是加载时确定的模型；图源于捕获的计算
P / D 分离P 和 D 各自运行一套上述 EngineCore/Worker/模型；connector 在 scheduler / runner 钩子处处理 KV 计划、加载、保存不是从 P 的某个 Python forward 直接跳进 D 的 forward
P 4DP×4TP / D 8DP×2TP常规部署分别有 4 / 8 个 DP EngineCore，及各 16 个 NPUWorker；EP 还可跨 DP 组通信每个 DP EngineCore 调度本组请求；TP Worker 参与同一执行计划，独立拥有本 rank 的权重/专家分片与缓存

vllm/v1/... 是 V1 Engine 命名空间，不等于 Model Runner V1；GPUModelRunner 的类名也不意味着 Ascend 正在使用 GPU。当前快照的 Runner 选择还支持环境变量显式覆盖与特性回退，判断实际路径以有效配置和日志/trace 为准。
