四类主线，加上服务边界观测

① 同步与 Host：S1 / S2 / S4 / S6，及层内依赖先区分 Host 阻塞、设备流依赖、collective 等待和后台输出 wait；优化目标是减少暴露等待，而不是删除所有同步。
② 算子与引擎：S2 准备、S3 目标层、S7 生成层模型侧做安全复用、已有融合接口替换、布局、多流、合法切分；框架侧查 Runner、准备、下发与图模式。重型核内瓶颈交接算子团队。
③ 快慢卡：跨阶段 X，落到准备、计算和通信同工作量计算差异、晚到 rank、通信慢、资源争用分别分析。不能把长 MegaMoE 或 dummy 等待直接认定为硬件慢卡。
④ 切分配置：调度、计算、KV 交接与生成固定资源预算和工作负载，比较 DP/TP/EP、batch/chunk、P/D 配比、缓存与 MTP；先记录配置实际生效值。

⑤ 网关排队 / KV传输 · F01/F02 · P2：入口排队挂在S0/S1，KV交接挂在S5/S6。联合网关、API、引擎与connector的请求级日志，补足worker profiling的范围；详见下方采集口径。

团队可以不重写 Attention / MegaMoE 核心内核，但不能跳过算子归因：调用条件、layout、转换、融合接口、batch 与输入到达时机仍由模型和框架控制。确认核内问题后，产出最小复现交接。

网关排队与KV传输：哪些需要补采？

worker Torch/NPU profiling主要描述被采进程与设备活动。完整请求链路还需要网关、API、引擎和connector的请求级日志/span；这些信息可与设备时间线关联。没有采到某段，表示未知，不代表该段耗时为0。

F01/F02初始列P2；若排队或KV加载等待主导TTFT、使D侧长期空等，或出现请求失败，应提升优先级。P2表示当前排期，不代表影响小。

网关/API排队 · S0单独的worker trace通常没有网关队列；NPU空闲不能反推请求在网关等。网关queue enter/leave、转发、API接收、处理线程/分词以及request_id/attempt。真队列出队−入队；API前处理与上游网络另计。F01
引擎等待 · S1 / S6设备时间线不能独立区分引擎排队、KV未就绪或无请求；worker通常看不到全部scheduler状态。引擎入队/首次调度、等待原因、抢占、版本支持的queue指标，关联实际请求。首次调度−引擎入队；重调度/外部KV等待另列，核对版本定义。F01 / G03
P/D KV交接 · S5 / S6可能看到connector线程、同步调用、通信或Hixl/拷贝事件；可见范围取决于采集进程与后端，不保证含完整请求标识。P/D两端、Transfer Engine/connector日志、KV ready/提交/完成/可消费时间、cache group与字节数。KV请求→D侧可用，拆等待P产出、排队/建链、搬运、额外放置/确认；传输带宽单独算。F02
Store池化读写 · S1 / S5部分读写/拷贝可见；lookup、租约、SSD回读和后台保存不一定在NPU trace中。Store lookup/load/save、键/缓存组、命中来源、字节数、错误/超时和异步完成。P2P与Store分开；冷/热、本地/外部命中、读/写与重算分开；保存未必阻塞当前TTFT。F02 / D04
  • 采集字段：request_id、remote_request_id、attempt、host/rank、阶段名、开始/结束、cache group/block、字节数、connector与结果状态；不用用户prompt正文来关联。
  • 同一进程优先用单调时钟算局部耗时；跨机器拼时间线先校准时钟并记录误差，不能直接相减未对齐的日志时间。
  • 真实KV ready/加载完成以数据可消费事件为准，异步API返回只代表提交；分层流水允许P计算、传输与D消费重叠。
  • TTFT按同一请求的关键依赖解释，不把网关、引擎、KV和device窗口中相互重叠的部分重复累计。

责任人与预期收益怎么填

分析任务，也是一项可验收的工作

直接性能收益记为 0。预期产物是定位证据、支持矩阵、可回收时间预算、实验设计或排除结论；不强行给每项分析填写加速百分比。

优化候选只填写方向、指标和验收条件。实现完成、功能通过、端到端性能通过是不同状态。

收益只从可回收关键路径估算

所有同步时长、算子累加、Free 占比都不能直接作为优化收益。先找未被其他工作覆盖、且能消除的部分，再测客户端和容量指标。

教学示例，非实测：100 ms 关键路径中一段 10 ms 加速 2 倍，其余不变，总时延约 95 ms；若该段原本完全被覆盖，端到端收益可能为 0。
